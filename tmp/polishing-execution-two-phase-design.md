# 打磨与执行双阶段 Issue 设计（目标文档）

> 日期：2026-08-16
> 状态：草案，待审核确认后进入执行

---

## 1. 核心设计理念

> **以一个「目标 Issue」为中心容器 —— 打磨阶段的所有过程记录（决策、审计、改进）以评论形式附着其上、待解决事项（阻塞项）以正文 checklist 承载；执行阶段才将可执行的子任务拆分为独立 Issue，并以「目标 Issue 正文中所有阻塞项清零」作为父任务完成的唯一标志。**

背后思想：**CCPM（关键链项目管理）**——不追求完整 WBS 树形任务分解，而是围绕「什么在阻碍目标达成」组织扁平化清单。解决掉所有的阻塞项，事情就成了。轻量、聚焦、可回溯。

---

## 2. 两个阶段与门控边界

| | 打磨阶段 | 执行阶段 |
|---|---|---|
| **起点** | 需求提出 | 打磨审核通过 |
| **目标** | 明确业务时序（角色与行为）+ 程序改造方案 | 把方案变为可运行的交付 |
| **流程** | 需求提出 → 目标定义 → 方案讨论 → 决策记录 → 审核通过 | 登记计划 → 拆分任务 → 迭代开发（开发+测试循环）→ 交付 |
| **终点** | 审核通过（approved） | 交付完成（done） |

**门控**：门禁验收是唯一的阶段切换闸口（门禁由 PO 发起，见第 11 节）。
- 打磨阶段门禁有两大项：① 业务时序流程中角色与行为；② 程序的制作方案
- **单人模式**：由人类（PO）直接验收，可借助隔离审核辅助（见第 11 节）
- **多人模式**：第①项由 PO 角色验收，第②项由技术负责人角色验收
- **审核依据**：目标 Issue 正文中记录的验收标准 + 产出物 + 人工审核反馈
- **不通过** → 打回重做，回到打磨阶段
- **防自产自检**：审核执行采用隔离上下文（DSH 另建会话 / OpenCode 开子会话），审核结论由 PO 终审（见第 11 节）

---

## 3. 角色定义

五个角色，全部通过 DSH 的 Agent 承载，人机协作分工：

| 角色 | 打磨阶段职责 | 执行阶段职责 |
|---|---|---|
| **PO** | 定义目标、验收业务时序、主导决策 | 登记执行计划 |
| **架构师/技术负责人** | 设计技术方案、验收技术方案 | 技术把关 |
| **Dev** | 参与方案讨论 | 拆分任务、开发实现 |
| **QA** | 参与验收标准定义 | 测试验证、质量把关 |
| **审核者** | 执行阶段门控审核（PO/技术负责人兼任） | — |

> 单人模式下：一个 Agent 兼任所有角色，切换角色指令即可，人类自己验收。

## 4. 记录载体模型

**一条铁律：打磨阶段不产生任何独立 Issue，只产生一个 Goal Issue，其余全部附着其上。**

| 记录类型 | 所在阶段 | 载体 | 由谁写入 | 用途 |
|---|---|---|---|---|
| **目标** | 打磨 | 独立 Issue（Goal Issue） | PO Agent | 整个流程的根容器 |
| **决策** | 打磨 | Goal Issue 的**评论** | PO/架构师 Agent | 结构化摘要：背景/方案/结论/依据 |
| **审计** | 打磨 | Goal Issue 的**评论** | 审核者 Agent | 审核过程与结果（对照验收标准） |
| **改进项** | 打磨 | Goal Issue 的**评论** | PO/架构师 Agent | 决策后的结果与后续动作 |
| **阻塞项（=子任务清单）** | 打磨→执行 | Goal Issue 的**正文**（checklist） | PO/Dev Agent | 待解决事项进度，CCPM 承载 |
| **任务详情** | 执行 | 独立 Issue（Task Issue） | Dev Agent | 细粒度任务跟踪 |

**为什么这样设计：**
- **决策/审计/改进放评论**：决策是「过程产物」，依附于目标上下文才有意义。读者打开目标 Issue 即可回溯完整决策链，不会被一堆独立 Issue 打断，也不必用关联查询拼凑上下文。
- **阻塞项放正文**：正文是「当前状态」的权威视图，checklist 勾选直接反映进度；而 CCPM 中阻塞项就是进度计量的单元。
- **只有任务拆分为独立 Issue**：执行阶段需要状态流转（in-progress/blocked/done）、多 Agent 认领、评论测试结果，独立 Issue 才承载得动。

---

## 5. 子任务与阻塞项的合并

**阻塞项即子任务，不再另设子任务概念。**

- 目标 Issue 正文中的每一行 checklist（`- [ ] 解决 xxx`）就是一个子任务 / 待解决事项
- **完成判定**：父任务（Goal Issue）**只有在其所有阻塞项都勾选完成后才算完成** —— 没有例外，也不存在「完成了大部分就算完成」
- 执行阶段可按需将某个阻塞项**展开**为更细粒度的独立 Task Issue 跟踪（如「实现登录页面」拆成前端/后端/联调三个 Issue），但进度计量始终回到正文 checklist：**Task Issue 都完成了，才勾选对应阻塞项；所有阻塞项清零，父任务才 done**

## 6. 单一状态机（跨两阶段）

```
  打磨阶段                                   执行阶段
draft ──提交审核──► reviewing ──通过──► approved ──登记计划──► planned
  ▲                   │                                                    │
  │                   │ 不通过（打回）                            开始执行  ▼
  │                   ▼                                                    │
  │◄── rejected ◄──────┘                                          in-progress
                                                                           │
                                                            ┌──── 遇到阻塞 ─┤
                                                            ▼              │
                                                         blocked ──解除──►─┤
                                                                           │
                                                                           ▼
                                                              所有阻塞项清零 ──► done
```

- `rejected` 时回到打磨，改进项写评论、阻塞项在正文更新，再重走 reviewing
- `blocked` 是执行期状态，解除后回到 in-progress

## 7. 行为时序与使用节奏

> 一个核心原则：**人类是流程节奏的掌控者，Agent 是响应者**。Agent 识别、询问、等确认、再执行；绝不主动推动流程或替人类做决定。

### 7.1 使用节奏总则

```
人类 ──► 发起（提需求 / 想推进 / 要求记录 / 确认决策）
                │
                ▼
Agent ──► 识别（判断是否达到创建 Issue / 记录 / 门禁的节点）
                │
                ▼
Agent ──► 询问（"是否需要创建 Goal Issue？" / "请确认..."）
                │
                ▼
人类 ──► 确认 / 回答（决定下一步）
                │
                ▼
Agent ──► 执行（按确认执行 gh 操作 / 写评论 / 更新状态）
                │
                ▼
Agent ──► 汇报（"已创建 #N" / 进度审查结果 + 询问下一步）
```

### 7.2 打磨阶段对话时序（使用视角）

```
[1] 人类提出需求（"想做个周报汇总工具"）
[2] Agent 识别 → 询问："这是一个新目标，需要我创建 Goal Issue 吗？"
[3] 人类确认："创建吧"
[4] Agent 询问目标背景与验收标准：
    "目标是什么？验收标准有哪些？"
[5] 人类回答目标背景、验收标准
[6] Agent 记录到 Goal Issue（draft）+ 草稿隔离区
[7] 讨论深入（人类主导节奏）：
    人类谈论业务时序 / 技术方案
    Agent 识别决策点 → 询问："要记录这个决策吗？" → 人类确认 → 写入评论
[8] 人类想推进 → 说"看看进度" 或 "准备进入下一阶段"
    Agent 审查进度（读 Issue / 日志）→ 汇报 + 询问下一步：
    "当前状态：xxx。阻塞项 3 项未决。下一步建议：提交门禁 / 继续讨论，你定。"
[9] 人类决定提交门禁 → Agent 执行提交（reviewing）
[10] 隔离审核 + 人类（PO）终审 → 通过/打回
```

### 7.3 执行阶段对话时序（使用视角）

```
[1] 人类确认进入执行（"开始执行"）
    Agent 登记计划（planned）+ 询问任务拆分粒度
[2] 人类确认拆分方案 → Agent 展开 Task Issue
[3] 人类主导每个 Task 的开发节奏：
    Agent 认领/推进，遇到阻塞时汇报并询问处理方式
[4] 人类想了解进度 → Agent 审查并汇报（含阻塞项勾选状态）
[5] 所有 Task 完成后 → Agent 汇报 → 询问是否关闭 Goal Issue
[6] 人类确认 → Agent 勾选全部阻塞项 → done
```

### 7.4 行为时序全景（流程状态视角）

### 打磨阶段（DSH 会话 + Goal Issue）

```
[1] 人类提出需求 ──► DSH 会话启动
[2] PO Agent 创建 Goal Issue（draft）
    正文：目标描述 + 验收标准（业务时序/技术方案两大项）+ 阻塞项 checklist
[3] PO/架构师 Agent 与人类在 DSH 中讨论业务时序、技术方案
[4] 出现决策 ──► Agent 将结构化摘要（背景/方案/结论/依据）写入 Goal Issue 评论
[5] 环节产出物完成 → PO 发起门禁，状态 → reviewing
    （隔离审核执行：DSH 另建会话 / OpenCode 开子会话）
[6] 隔离审核对照正文验收标准核对产出物，产出审核结论，PO 终审
    通过 ──► 审计结论写评论，状态 → approved，打磨结束
    不通过 ──► 审计结论+改进项写评论，状态 → rejected，打回（改进项在评论、阻塞项更新正文）
```

### 执行阶段（Task Issue + 回到 Goal Issue）

```
[1] 人类确认进入执行 ──► 状态 → planned
[2] Dev Agent 将正文阻塞项拆分/登记为独立 Task Issue（细粒度），关联回 Goal Issue
[3] Task 独立流转：in-progress ⇄ blocked（解除后回）→ done
[4] QA 在 Task Issue 上评论测试结果
[5] 每个 Task done ──► 回到 Goal Issue 正文勾选对应阻塞项
[6] 所有阻塞项清零 ──► Goal Issue 状态 → done，交付完成
```

## 8. 与 DSH 的集成

- **讨论场所**：DSH 会话（人类与各角色 Agent 自由讨论，保持讨论流动性）
- **记录场所**：GitHub Issues（Agent 负责把讨论**结构化摘要**写入目标 Issue，不贴原始聊天记录，只做背景/方案/结论/依据的提炼）
- **Agent ↔ Issue 工具链**：各 Agent 通过 `gh` CLI（create/edit/comment/list）操作 Issue；角色对应关系：
  - PO Agent ↔ 创建/维护 Goal Issue、决策评论、业务时序验收
  - 架构师 Agent ↔ 决策评论、技术方案验收
  - Dev Agent ↔ Task Issue 维护、阻塞项勾选
  - QA Agent ↔ Task Issue 测试评论
  - 审核者 Agent ↔ 审计评论、状态切换（approve/reject）
- **门禁**：PO 驱动的产出物验收（见第 11 节）。隔离审核执行：DSH 另建会话、OpenCode 开子会话，PO 终审放行/打回
- **过程审计**：独立于门禁，监督过程、产出优化建议（见 `tmp/process-audit-design.md` + `tmp/process-audit-dual-session.md`）
- **跨会话日志查询**：`dsh-session-query` 的 `load(sessionId)` 可拉取指定会话的完整事件日志，作为门禁审核与过程审计的证据链

## 9. 单人 vs 多人的差异

| 维度 | 单人模式 | 多人模式 |
|---|---|---|
| Agent | 一个 Agent 兼任全部角色 | 各角色独立 Agent |
| 验收 | 人类（PO）亲自验收（对照正文验收标准，可借助隔离审核辅助） | PO 验收业务时序，技术负责人验收方案 |
| 门禁隔离 | DSH 另建会话 / OpenCode 开子会话（见第 11 节） | DSH 另建会话 / OpenCode 开子会话 |
| 过程审计 | 独立监督，产出优化建议（见 process-audit 文档） | 独立监督，产出优化建议 |
| 记录 | 无差别，同样写入 Goal Issue | 无差别，同样写入 Goal Issue |
| 目的 | 个人项目轻量自管 | 团队协作、责任到角色 |

## 10. 打磨阶段的本质：人类 + 副手深度讨论

> 2026-08-16 洞察记录

在 AI Agent 时代重新审视打磨阶段，可以看到一个更本质的分工模式：

### 个人开发者

打磨阶段不需要多 Agent 隔热。**人类只需与 AI 副手（Agent）多次讨论完成打磨**。人类提出需求、表达想法、质疑方案；AI 副手提供分析、梳理方案、记录决策。两者之间是深度对话关系，不需要引入 PO、架构师等多角色——因为人数就一个人，角色都在人类自己脑子里。

### 中小规模团队

打磨阶段的「副手角色」由**技术接头人（Tech Lead / 技术负责人）** 扮演。他是人与 AI 之间的桥梁：

- 他代表团队与 AI 讨论：转化业务诉求为技术目标、评审 AI 产出的方案
- 他代表 AI 向团队解释：A/B 方案取舍的技术依据、技术决策的边界与影响
- 他负责把关：方案是否符合团队的技术栈规范、是否与现有架构兼容

本质上，无论团队规模多大，**打磨阶段的讨论只有一个「核心对话对」**：人类（或技术接头人）↔ AI Agent。多人模式下 PO 验收业务时序、技术负责人验收技术方案，是**门控动作**而非**讨论过程**——讨论过程始终是单对单的。

### 对设计的影响

这个洞察意味着：

- **打磨阶段的 Agent 不需要多角色隔离**：一个 Agent 副手 + 角色指令切换即可胜任全部打磨工作
- **多 Agent 的价值在执行阶段**：复杂任务拆分后，不同角色（Dev、QA 等）独立执行，才需要系统级的角色隔离
- **技术接头人模式是团队使用 AI 的最佳实践**：一个人负责与 AI 深度对话，其他人集中在自己的专业领域，降低协同成本

## 11. 门禁（Gate）：PO 发起的产出物质量验收

> 2026-08-19 更新：门禁与过程审计拆分为两个独立概念。本文档第 11 节为**门禁**；**过程审计**（独立监督、过程优化）见 `tmp/process-audit-design.md` 与 `tmp/process-audit-dual-session.md`。

### 11.1 门禁的定位

| 维度 | 内容 |
|------|------|
| **发起与跟进** | **PO（人类角色）** 发起和跟进 |
| **依据** | PO 定义的**验收标准**（记录在 Goal Issue 正文） |
| **机制** | 每个流程环节产出一个**产出物**，验收产出物质量 |
| **目的** | 确保每个环节的产出能保证最终软件质量 |
| **关注对象** | 产出物（文档、方案、代码、测试结果） |

PO 需要知道产品质量如何验收、定义验收标准、掌握研发流程，通过流程管理保证软件质量。

### 11.2 验收机制

```
流程环节 ──► 产出物 ──► 对照验收标准 ──► 放行 ──► 下一环节
                        │
                        └── 打回 ──► 返工
```

验收节点示例：

| 环节 | 产出物 | 验收标准（PO 定义） |
|------|--------|-------------------|
| 打磨-目标定义 | 目标描述 + 验收标准 | 目标清晰、边界明确 |
| 打磨-方案讨论 | 业务时序 + 技术方案（定稿） | 业务时序角色与行为明确；方案确认 |
| 打磨-审核 | Goal Issue 全量记录 | 阻塞项清零、决策/审计记录完整 |
| 执行-任务完成 | 实现代码 + 测试结果 | 任务验收标准通过 |
| 交付 | 交付物 + 文档 | 全部阻塞项清零 |

### 11.3 隔离审核（防自产自检）

门禁审核**仍需隔离上下文**（期望独立模型判断，不被制作过程污染）：

- **DSH**：另建会话审核（双会话文件桥接，`checkpoint.json` / `audit.json` 交换审核结论）
- **OpenCode**：开子会话审核（子代理独立上下文执行审核）

**审核执行与终审权分离**：隔离审核给出审核结论（通过/不通过），**PO（人类）终审决策**放行或打回。即使审核 Agent 建议通过，PO 仍可否决。

### 11.4 与过程审计的边界

| | 门禁（Gate） | 过程审计（Process Audit） |
|--|------------|--------------------------|
| **目的** | 验收产出物质量 | 监督过程、发现可优化环节 |
| **产出** | 放行 / 打回 | 过程优化建议 |
| **驱动** | 驱动状态流转 | 不驱动状态流转 |
| **发起者** | PO（人类角色） | 独立监督角色 |
| **是否需隔离** | ✅ 是（DSH 另建会话 / OpenCode 开子会话） | ✅ 是（双会话设计） |
| **文档** | 本节 | `tmp/process-audit-design.md` + `tmp/process-audit-dual-session.md` |

> 两者都需会话隔离，但目的不同：门禁隔离审核产出「放行/打回」，过程审计隔离产出「优化建议」。

## 12. 产出物草稿隔离：未定稿前的保护（设计想法）

> 2026-08-16 洞察记录：打磨阶段中新目标建立时，产出物文档未有完整定论前，应标记为草稿并隔离，避免污染正式项目上下文。具体方案见落地改造方案。

### 12.1 问题

打磨阶段的目标讨论处于「进行中」状态时，相关产出物文档（业务流程、技术方案等）的**内容尚不成熟**，此时不应直接写入正式项目文档目录。否则：

- 正式文档被不成熟的方案内容污染，读者难以区分哪些是定稿、哪些是讨论中
- 多人协作时，他人可能误将草稿内容当作正式决策引用
- 被打回/废弃的目标，其残留的草稿内容需手动清理

### 12.2 核心想法

新目标建立到 Issue，但产出物文档未有完整定论时：

- **标记为草稿**：Goal Issue 打 `draft` 标签，与 `reviewing`/`approved` 状态区分
- **隔离存放**：产出物写入隔离区（`.ai-engineering/drafts/`），不污染正式项目文档目录
- **定稿后才正式化**：方案明确后，从隔离区复制到正式目录，移除草稿标记

> **目录名语义**：`.ai-engineering/` 是固定名称，标识「ai-engineering 研发工程体系」在工作区的落地痕迹，**不跟随宿主项目名**（类比 `.git/` 固定名），也于工具无关。

### 12.3 对打磨阶段流程的影响

```
打磨阶段（细化）
│
├─ 草稿期（draft）
│    ├─ 目标提出 → 创建 Goal Issue（draft）
│    ├─ 讨论决策 → 记录到 Issue 评论
│    ├─ 产出物文档 → 写入 .ai-engineering/drafts/（隔离区，不污染正式目录）
│    └─ 方案未定 → 继续讨论
│
├─ 定稿期（reviewing）
│    ├─ 方案已明确
│    ├─ 产出物从隔离区复制到正式项目文档目录
│    └─ 提交审核
│
└─ 审核通过（approved）/ 打回（rejected）
```

> 具体隔离区的目录结构、与 skill 的衔接、与门禁流程的配合：见落地改造方案中「产出物草稿隔离方案」章节。

## 13. 跨工具使用（设计想法）

> 2026-08-16 洞察记录：这套双阶段方案希望跨 AI 编程工具使用，而非绑定单一工具。

### 13.1 动机

用户日常以 **OpenCode** 和 **DSH** 为主要编码工具，**Codex** 与 **Claude Code** 为辅助。方案设计不绑定单一工具：

- 打磨讨论可能发生在任意一个工具中（哪顺手用哪个）
- 执行开发可能在不同工具间切换（DSH 做主流程、OpenCode 做特定操作）
- 门禁的隔离审核（或过程审计）可能与制作会话不在同一工具中

### 13.2 跨工具的基础：工具无关载体

方案的核心载体天然跨工具：

| 载体 | 工具无关性 |
|------|-----------|
| GitHub Issues（Goal Issue、评论、标签） | ✅ 任何工具通过 `gh` CLI 或 API 操作 |
| 文件系统（`.ai-engineering/gate/` 桥接、`.ai-engineering/drafts/` 隔离区） | ✅ 任何工具读写同一工作区文件 |
| AGENTS.md（工作区指令） | ✅ OpenCode / DSH / Codex 均支持 |
| Markdown 文档（产出物） | ✅ 与工具无关 |

### 13.3 工具差异的边界

工具的**自动化增强能力**各有不同（多 Agent 角色、会话隔离、日志审计等），这是**适配层**的差异，不改变核心流程：

| 能力 | DSH | OpenCode | Codex / Claude Code |
|------|-----|----------|---------------------|
| 项目级 Agent 角色发现 | preset 配置 | `.opencode/agents/*.md` 自动发现 | 各自原生机制 |
| 跨会话审计日志 | `session-query` | 无原生 | Codex 跨会话沟通 |
| 实时审查副模型 | `dsh-advisor` 插件 | 无原生 | 无原生 |

> 具体分层（通用层 / 工具适配层）与落地建议：见落地改造方案中「通用层与工具适配层」章节。

## 附录：术语对照

| 术语 | 含义 |
|------|------|
| Goal Issue | 目标 Issue，每个需求的根容器，承载打磨阶段所有记录和执行阶段进度 |
| 阻塞项 | 正文 checklist 中的一行，= 一个子任务，全部清零才算完成 |
| 决策 | 讨论中的方案选择，结构化摘要写入评论 |
| 审计 | 审核过程与结果，写入评论 |
| 改进项 | 决策后的后续动作，写入评论 |
| Task Issue | 执行阶段独立 Issue，跟踪细粒度任务 |
| CCPM | 关键链项目管理，围绕阻塞项组织进度 |
| 打回 | 审核不通过，回到打磨阶段，状态 → rejected |
| 门禁（Gate） | PO（人类角色）发起的产出物质量验收：对照验收标准 → 放行/打回 |
| 过程审计 | 独立于门禁：监督过程、发现可优化环节、产出过程优化建议（见 `tmp/process-audit-design.md`） |
| 隔离审核 | 门禁/审计的执行方式：DSH 另建会话、OpenCode 开子会话，独立模型判断 |
| checkpoint | 副手会话写入的阶段完成信号（`.ai-engineering/gate/checkpoint.json`） |
| audit.json | 隔离审核写入的结论（门禁：放行/打回；过程审计：改进建议） |
| 副手会话 | 制作实例，负责打磨讨论与执行开发 |
| session-query | DSH 跨会话日志查询服务，拉取副手会话完整事件日志作为审计证据链 |
| 草稿期（draft） | 目标提出但产出物未定稿的阶段，产出物写入隔离区 |
| 草稿隔离 | 产出物未定稿前写入隔离区（`.ai-engineering/drafts/`），不污染正式项目文档 |
| 通用层 | 不依赖任何工具的设计理念与流程规范（GitHub Issues + 文件系统承载） |
| 工具适配层 | 依赖特定工具特性的自动化增强（preset 配置、session-query、`.opencode/agents/` 等） |
