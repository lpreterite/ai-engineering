# Issue 记录规则（子任务 1 草案）

> 对应任务 T-20260803-002，子任务 1：规范驱动的 Issue 管理
> 日期：2026-08-04

---

## 1. 定位

- **Issue** = 人机交互过程的记录载体
- **MD 文档** = 决策结果的产物载体
- 核心原则：**过程与结果分离**

Issue 记录"过程"（骨架 + 过程评论），MD 文档记录"结果"（决策产物）。

---

## 2. Issue 正文（五字段抽象层）

所有 Issue 类型共享此抽象层，类型专属模板在此基础上组织内容。

### 2.1 目标

从会话结论提炼。一句话说清楚"为什么做这个"。

**示例**：

> 实现团队周报自动汇总功能，解决手动收集周报效率低、格式不统一的问题。

### 2.2 范围（In / Out）

明确做什么和不做什么。

**示例**：

| In | Out |
|----|-----|
| 周报模板配置 | 周报内容智能摘要（AI 自动总结） |
| 自动提醒与收集 | 与第三方工具（飞书/钉钉）集成 |
| 汇总文档生成 | 历史周报数据趋势分析 |
| 基础权限控制（仅负责人可查看汇总） | 自定义审批流程 |
| 邮件通知 | 移动端 App |

### 2.3 验收标准

满足什么条件算做成。功能/行为层面的可验证条件，每条可独立检查。

**示例**：

> - 系统自动在每周五 18:00 向所有团队成员发送周报提醒
> - 成员可通过指定链接填写周报，支持 Markdown 格式
> - 系统自动汇总所有成员周报，生成一份合并文档
> - 汇总结果自动发送给团队负责人

### 2.4 依赖/开放问题

前置上下文：关联 Issue、项目文档链接、待确认项。

**示例**：

> - 依赖：团队通讯录接口需先完成（关联 Issue #15）
> - 待确认：周报模板格式需与各团队负责人沟通确认
> - 参考文档：[团队协作规范](../guide/03-collaboration.md)
> - 开放问题：邮件发送服务使用公司 SMTP 还是第三方 API？

### 2.5 完成定义（DoD）

从交付角度补充，描述"怎样算做完"。

| 子项 | 说明 | 示例 |
|------|------|------|
| **Minimum design** | 本批次验收所需的最小必要设计方案（避免过度设计） | 使用 Markdown 模板 + 邮件发送，不做富文本编辑器 |
| **Explicitly not doing** | 本批次明确不做的事（交付层面，呼应 Scope Out） | 不做企业微信/飞书推送，不做 AI 自动摘要 |

## 3. Issue 评论（状态卡结构）

Issue 评论采用**状态卡（Status Card）**结构。每条评论即一张状态卡，对应一次状态流转。

**强制规则**：每次状态流转必须生成一张状态卡。

**状态卡与状态标签的分工**：
- 状态标签（`status/*`）→ 标记当前状态
- 状态卡 → 记录流转依据（审计 + 决策）

### 3.1 状态卡结构

```
**状态卡 #<评论编号> | <状态流转> | <时间戳>**

状态变化
- <当前状态> → <新状态>

审计 （必填）
- 完成关键事项：[...]
- 证据链（自包含，无需翻聊天记录）：
  - 产出物：[文件路径/文档名] + 关键内容摘要
  - 关键上下文：[一句话背景，说明这一步的由来]
  - 关键引用：[决策性金句 1-2 句，不引过程闲聊]（若适用）
  - 验证方式：[测试 / 人工确认 / 评审]
  - 关联：[Issue #N / 文档链接 / 会话片段]

决策 （可选，本次流转涉及时填写）
- 决策：[内容]
- 依据：[为什么这么做]
- 影响：[影响范围]
```

### 3.2 审计块（必填）

记录**进度变化及其依据**——完成的关键事项、状态流转，以及自包含的详尽证据链。目的是给人类对 AI 工作进度进行审计验收，读一条即可接上上下文，无需回溯聊天记录。

**示例**：

```
状态变化
- open → in_progress（进入开发）

审计
- 完成关键事项：需求分析完成，PRD-v1.0 定稿
- 证据链：
  - 产出物：docs/product/PRD-v1.0.md（含 5 条用户故事 + 验收标准）
  - 关键上下文：用户提出周报收集费劲，经讨论确认范围不含 AI 摘要
  - 关键引用：「汇总结果发给负责人就行」→ 决定"仅负责人可查看"权限边界
  - 验证方式：PRD 与用户逐条核对确认
  - 关联：#15 通讯录接口依赖
```

### 3.3 决策块（可选）

记录本次流转中做的决策——为什么这么做。

**示例**：

```
决策
- 决策：采用 Markdown 作为周报输入标准
- 依据：团队已有 Markdown 使用习惯，实现成本低
- 影响：汇总解析逻辑基于 Markdown 语法
```

## 4. 与 YAML 模板的关系

### 4.1 类型收敛

打磨族类型清零，Issue 类型收敛为执行族：

| 原类型 | 处理 | 去向 |
|--------|------|------|
| **Decision** | ✂️ 移除 | 决策 → 状态卡决策块 + MD 文档 |
| **Review** | ✂️ 移除 | Gate 验收在对话中完成，结论转化为任务 Issue |
| **Question** | ✂️ 移除 | 依附带主题的讨论，待确认项 →「依赖/开放问题」字段 |
| **Risk** | ✂️ 移除 | 风险作为依赖/范围处理，不设独立类型 |

### 4.2 剩余模板

执行族 Issue 类型基于五字段抽象层组织类型专属内容：

| 模板 | 调整 |
|------|------|
| **Bug** | 保留。五字段基础上补充：复现步骤、环境、预期/实际行为 |
| **Feature** | 保留。五字段基础上补充：动机、备选方案 |
| **Task** | 保留。五字段基础上补充：分类（重构/文档/配置/CI/测试等） |
| **Epic** | 新增（GitHub 原生类型，非 YAML 文件）。大型工作拆分为 Sub-issues 时使用 |
| **config** | 保留。`config.yml` 用于控制 Issue 创建入口（空白 Issue 禁用、指向 Discussions） |

## 5. AI 类型判断规则

AI 根据会话内容自动判断 Issue 类型，无需人工指定。

| 判断信号 | 类型 |
|----------|------|
| 有明确的缺陷描述 + 复现步骤 | Bug |
| 有功能需求描述 + 验收标准 | Feature |
| 纯工程任务（重构/文档/配置/CI/测试） | Task |
| 大型工作，需拆分为多个子任务 | Epic |

**仲裁规则**：若判断信号重叠（如"重构但存在开放问题"），优先按"当前最明确的判定"定类型，开放问题记录在「依赖/开放问题」字段中，不作为类型判断依据。

## 6. 触发与工作流

### 6.1 触发（双通道）

| 通道 | 说明 |
|------|------|
| **人喊话** | 人类主动要求记录，对话中自然语言信号："记录一下" / "建个 Issue" / "把这个记下来" / "提个 Issue" |
| **流程节点识别** | AI 识别到关键进度节点（如 PRD 完成、Gate 通过、状态流转），**主动询问**人类确认后记录 |

### 6.2 创建 Issue 工作流

```
触发（人喊话 / 流程节点识别后确认）
  │
  ├─ ① 捕获当前会话上下文（总结 + 关键金句）
  │
  ├─ ② 提取五字段
  │     目标 ← 会话结论
  │     范围 ← 做什么/不做什么
  │     验收标准 ← 可验证的条件
  │     依赖/开放问题 ← 关联链接 + 待确认项
  │     完成定义 ← Minimum design + Explicitly not doing
  │
  ├─ ③ AI 自动判断类型（Feature / Task / Bug / Epic）
  │     按对应模板补充类型专属字段
  │
  ├─ ④ 展示给人类确认
  │
  ├─ ⑤ 确认后 gh issue create
  │     创建即生成状态卡 #1
  │
  └─ ⑥ 后续状态流转时，强制生成状态卡
        审计块（必填）+ 决策块（可选）
```

### 6.3 状态卡生成规则

- **强制**：每次状态流转必须生成一张状态卡
- 触发：人喊话 或 流程节点识别后询问确认
- 编号：使用 GitHub 评论自身编号

## 7. 完整示例

### 场景

用户与 AI 对话："最近团队周报收集太费劲了，每个人格式不一样，汇总要花半小时。能不能做个自动收集的工具？"

### 创建的 Issue

```
标题：[Feature] 团队周报自动汇总功能

## 目标
实现团队周报自动汇总功能，解决手动收集周报效率低、格式不统一的问题。

## 范围
In: 周报模板配置、自动提醒与收集、汇总文档生成、基础权限控制、邮件通知
Out: AI 智能摘要、飞书/钉钉集成、历史趋势分析、自定义审批流程、移动端 App

## 验收标准
- 系统自动在每周五 18:00 向所有团队成员发送周报提醒
- 成员可通过指定链接填写周报，支持 Markdown 格式
- 系统自动汇总所有成员周报，生成一份合并文档
- 汇总结果自动发送给团队负责人

## 依赖/开放问题
- 依赖：团队通讯录接口（#15）
- 待确认：周报模板格式需与各团队负责人沟通
- 参考：团队协作规范
- 开放：邮件发送使用 SMTP 还是第三方 API？

## 完成定义
Minimum design: Markdown 模板 + 邮件发送，不做富文本编辑器
Explicitly not doing: 不做企业微信推送，不做 AI 自动摘要
```
