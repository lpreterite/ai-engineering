## 1. 概述

### 1.1 软件研发流程阶段

AI 软件研发流程分为两大阶段：

| 阶段 | 核心目标 | 人类参与度 | 记录载体 |
|------|----------|-----------|---------|
| **打磨阶段** | 定义"做正确的事" | 深度参与 | Goal Issue + 产出物草稿隔离 |
| **执行阶段** | "正确地做事" | 关键节点介入 | Task Issue + Goal 阻塞项勾选 |

### 1.3 核心设计原则

| 原则 | 说明 |
|------|------|
| **人类主导节奏** | 人类是流程掌控者，Agent 遵循「识别→询问→确认→执行→汇报」循环 |
| **Goal Issue 根容器** | 打磨阶段的决策/审计/改进全部以评论附着于 Goal Issue，不产生独立打磨族 Issue |
| **阻塞项 = 子任务** | Goal 正文的阻塞项 checklist 同时是子任务清单，全部清零才 done |
| **产出物草稿隔离** | 产出物未定稿前写入 `.ai-engineering/drafts/`，定稿（人类批准）后复制到正式目录 |
| **门禁 PO 驱动** | 门禁由 PO（人类角色）发起，隔离审核给出结论，PO 终审放行/打回 |

## 2. 打磨阶段详解

### 2.1 打磨阶段角色分工

| 环节 | 人类负责 | Agent 负责 |
|------|----------|------------|
| 需求提出 | ✅ 发起需求 | 识别目标，询问是否创建 Goal Issue |
| 目标定义 | ✅ 回答目标背景、验收标准 | 记录到 Goal Issue（draft） |
| 业务时序讨论 | ✅ 主导讨论、确认决策 | 识别决策点，询问是否记录 |
| 技术方案讨论 | ✅ 主导讨论、确认选型 | 记录决策评论，更新草稿 |
| 产出物定稿 | ✅ 批准定稿 | 从隔离区复制到正式目录 |
| 门禁 | ✅ PO 发起 + 终审 | 隔离审核执行（DSH 另建会话 / OpenCode 开子会话） |

### 2.2 打磨阶段时序

```
[1] 人类提出需求
[2] Agent 识别 → 询问："需要创建 Goal Issue 吗？"
[3] 人类确认 → Agent 询问目标背景与验收标准
[4] 人类回答 → Agent 记录到 Goal Issue（draft）+ 草稿隔离区
[5] 讨论业务时序、技术方案（人类主导节奏）
    - 出现决策 → Agent 询问 → 人类确认 → 写入 Goal Issue 评论
[6] 人类想推进 → Agent 审查进度 → 汇报 + 询问下一步
[7] 人类决定提交门禁 → Agent 检查定稿条件（无未决项 + 产出物定稿）
[8] 产出物定稿（人类批准）→ from .ai-engineering/drafts/ 复制到正式目录
[9] 状态 → reviewing，隔离审核执行
[10] 审核结论 → PO 终审：approved / rejected
```

### 2.3 门禁验收（Gate → 门禁）

**旧模型**中打磨阶段有 Gate 1（PRD 验收）、Gate 2（里程碑验收）两个门控。
**新模型**中门禁是**一个 PO 驱动的产出物验收环节**，不再按 Gate 编号切分：

| 维度 | 旧 Gate 模型 | 新门禁模型 |
|------|-------------|-----------|
| 发起者 | Agent 流程触发 | **PO（人类角色）发起** |
| 依据 | 检查清单（G1-01 等） | Goal Issue 正文验收标准 + 产出物 |
| 审核者 | 逐步人工核对 | **隔离审核**（DSH 另建会话 / OpenCode 开子会话）+ PO 终审 |
| 产出 | Gate 通过标记 | approved / rejected（状态标签） |
| 频率 | 每阶段一次 | 每产出物完成时 |

**门禁验收流程**：

```
产出物完成 → PO 发起门禁 → 状态 reviewing
    │
    ├─ 隔离审核（独立上下文）：
    │    ① 读 Goal Issue 验收标准 + 产出物
    │    ② 逐项核对（业务时序 / 技术方案）
    │    ③ 产出审核结论
    │
    ├─ PO 终审：
    │    通过 ──► approved（进入下一环节）
    │    打回 ──► rejected（返工，改进项写评论）
```

### 2.4 重做机制

门禁验收不通过时（rejected）：

- 改进项写入 Goal Issue 评论
- 阻塞项在正文更新
- 返工后重新提交门禁

## 3. 执行阶段详解

### 3.1 执行阶段特点

- **人类主导节奏**：每个环节由人类发起，Agent 记录与执行
- **Task Issue 承载**：从 Goal 阻塞项展开，独立流转状态
- **阻塞项回勾**：Task done → Goal 正文勾选对应阻塞项

### 3.2 执行阶段流程

```
人类确认进入执行 → Goal 状态 planned
    │
    ▼
Agent 询问任务拆分粒度 → 人类确认
    │
    ▼
Agent 创建 Task Issue（自包含规范：背景/目标/任务/验收标准/关联/完成定义）
    │
    ▼
Task 独立流转：
  in-progress ⇄ blocked（遇阻塞汇报，人类决定处理方式）
       │
       ▼
  done（QA 验证通过，测试结果写 Task 评论）
    │
    ▼
回到 Goal 正文勾选对应阻塞项
    │
    ▼
所有阻塞项清零 → Agent 汇报 → 人类确认 → Goal done
```

### 3.3 分歧处理机制

| 场景 | 处理方式 |
|------|---------|
| 任务遇阻塞 | Agent 汇报阻塞原因，人类决定处理方式 |
| QA 不通过 | 在 Task 评论记录缺陷，退回 Dev 修复后重新验证 |
| 跨任务依赖 | 依赖未决时先确认决策，再展开任务 |

## 4. 与旧模型的迁移对照

| 旧概念 | 新概念 | 迁移路径 |
|--------|--------|---------|
| Gate 1（PRD 验收） | 门禁验收（产出物级） | 打磨完成统一走门禁（PO 驱动） |
| Gate 2（里程碑验收） | 门禁验收（产出物级） | 同上 |
| Gate 3 / Gate 4 | 执行阶段 QA + 交付完成 | 对应 Task 验证 + 阻塞项清零 |
| 打磨族 Issue（Decision/Question/Risk/Review） | Goal Issue 评论 | 决策/审计/改进写入 Goal Issue 评论 |
| 执行族 Issue（Feature/Task/Bug） | Task Issue | 从 Goal 阻塞项展开 |
